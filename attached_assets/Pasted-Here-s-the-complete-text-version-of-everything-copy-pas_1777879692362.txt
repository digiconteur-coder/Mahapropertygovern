BPC — BHARAT PROPERTY CHAIN
SECURITY ARCHITECTURE & DATA FRAMEWORK
Complete Technical Brief — Ministry of Housing & Urban Affairs

SECTION 01 — THE REAL QUESTION
What the Ministry Is Actually Asking
Before explaining any technology, let’s name the three fears the Ministry has and address each one directly and honestly.

FEAR 01 — Can someone hack this and change a property record?
Answer: No.
Because property records are never stored in only one place. The system uses a method called cryptographic hashing — the same technology used by SBI, HDFC, and every Indian bank for internet banking. Any change to any record, even one character, creates a completely different hash fingerprint, which immediately triggers an alert across all storage nodes. You cannot silently edit a record. The tamper is always visible, always logged, always traceable.

FEAR 02 — Is blockchain legal in India? Can it be used as legal evidence?
Answer: We do not use blockchain as a legal record.
We use it as an audit infrastructure layer — meaning it is the system that logs who did what, when, and what the record looked like at that exact moment. It is an internal tamper-proof logbook. The legal record remains the Sub-Registrar’s office, exactly as it has always been. BPC adds a shadow copy alongside it that cannot be altered. Courts already accept digital evidence under Section 65B of the Indian Evidence Act. No new law is required.

FEAR 03 — What if the BPC company itself turns corrupt? Can insiders manipulate records?
Answer: No single person — including BPC’s own engineers — can change a record without leaving an irremovable trace.
The system is designed so that every action by every user, every admin, and every government officer creates a permanent log entry. Deleting a log entry is technically impossible because logs are written simultaneously across multiple independent nodes. The government’s own designated node is one of those nodes. The government is a co-owner and co-custodian of the audit trail. BPC cannot manipulate records unilaterally.

SECTION 02 — THE 7-LAYER SECURITY ARCHITECTURE
The Seven Walls a Hacker Must Break — Simultaneously
BPC is not protected by one security system. It uses 7 independent layers. To succeed, an attacker must break all 7 at the exact same time. That is computationally and practically impossible.

LAYER 1 — Identity Verification
Components: Aadhaar OTP Login, Biometric Verification, Role-Based Access Control (RBAC), Device Fingerprinting, Session Tokens (JWT)
What this means: Who you are is verified before you touch any data. A government revenue officer has different access permissions than a citizen. A citizen cannot see an officer’s dashboard. An officer cannot access another state’s records without authorization. Every login attempt is logged. Every failed login attempt is flagged.

LAYER 2 — Data Transmission Security
Components: TLS 1.3 Encryption, Certificate Pinning, API Gateway with Rate Limiting, IP Whitelisting for Government Nodes
What this means: All data moving between users and servers is encrypted using TLS 1.3 — the same standard used by NPCI for UPI transactions. It cannot be intercepted in transit. Certificate pinning means a hacker cannot impersonate BPC’s servers. Rate limiting means automated attack tools are blocked before they can probe the system.

LAYER 3 — Application-Level Hardening
Components: Input Validation blocking SQL Injection attacks, OWASP Top 10 compliance, AI-powered Document Forgery Detection, Quarterly Automated Penetration Testing
What this means: The software itself is hardened against all known attack types. SQL injection — the most common database attack — is blocked at the code level before it reaches any data. The OWASP Top 10 is the internationally recognized standard for secure application development. BPC is certified compliant. Penetration testing means we pay ethical hackers to try to break our system every quarter and fix what they find.

LAYER 4 — Data Storage Security
Components: AES-256 Encryption at Rest, Encrypted PostgreSQL for property metadata, Document hashes stored on-chain, Physical documents in encrypted cloud storage with offline backup
What this means: Even if someone physically steals the hard drive from BPC’s server, they get completely unreadable encrypted data. AES-256 is the encryption standard used by the US military and every major Indian bank. The encryption keys are stored separately in a Hardware Security Module — a dedicated physical device that holds cryptographic keys and cannot be remotely accessed.

LAYER 5 — Blockchain Audit Infrastructure
Components: Permissioned Private Blockchain Log, Multi-Node Architecture (BPC Server + Government Node + NIC Node), Every action creates an immutable entry, Hash chaining where each block references the previous one
What this means: The logbook that cannot be erased. Every transaction’s fingerprint is spread simultaneously across 3 or more independent servers owned by different entities. BPC cannot edit the government’s copy. The government cannot edit BPC’s copy. Both are required to match at all times. Any mismatch triggers an immediate automated alert.

LAYER 6 — Legal Digital Signatures
Components: IT Act 2000 compliant Digital Signatures, NIC eSign Integration, e-Stamp State Government API, Aadhaar eSign via UIDAI
What this means: Every document signed on BPC is legally valid under Indian law and admissible in any Indian court. This is the exact same standard used by DigiLocker. A buyer signing an Agreement to Sale on BPC has the same legal standing as signing a physically stamped document — because Aadhaar eSign and IT Act digital signatures carry full legal weight under Indian law.

LAYER 7 — Human Oversight and Final Authority
Components: Government Officer holds final decision authority, 4-Eyes Verification requiring two officers for all critical operations, AI flags anomalies for human review, Zero automated write access to Registrar records
What this means: Technology assists. Humans decide. No automated action in BPC can change a legal property record. All critical actions require an authorized government officer’s digital signature. The AI detects suspicious patterns and flags them. A human officer reviews and makes the final call. The system is designed to make officers more powerful and informed — not to remove them from the process.

CRITICAL POINT FOR MINISTRY:
These 7 layers are independent of each other. The failure of one layer does not compromise the entire system. This is called Defense in Depth — the same architecture used by NPCI for UPI, by UIDAI for Aadhaar, and by Indian banks for core banking. BPC follows the exact same security standard as existing trusted government digital infrastructure.

SECTION 03 — BLOCKCHAIN: WHAT IT DOES AND WHY
Explained for a Minister — No Technical Jargon
First, what blockchain is NOT in BPC:
	•	It is not the legal title record
	•	It is not a cryptocurrency
	•	It is not replacing the Sub-Registrar
	•	It has nothing to do with Bitcoin or speculation
What it IS:
A permanent, distributed logbook — like a notarized diary that is simultaneously held by multiple trusted parties and cannot be edited after it is written.

REAL EXAMPLE: What happens when Ramesh sells his flat to Priya
Property: Flat 402, Sunrise Tower, Andheri, Mumbai
BPC-ID assigned: BPC-MH-2024-00847361
Step 1 — When the sale deed is finalized, the document is mathematically processed to produce a unique fingerprint called a hash. Example hash: a3f8d1c9e2b74f92a1… (this is a 256-character string unique to this exact document)
Step 2 — A block is written to the audit chain containing:
	•	Seller name: Ramesh
	•	Buyer name: Priya
	•	Date and exact time: 14-March-2025 at 14:32:07 IST
	•	Sale deed hash: a3f8d1c9e2b74f92a1…
	•	Sub-Registrar verification status: Confirmed
	•	Officer digital signature: [encrypted]
	•	Previous block reference: [hash of the block before this one]
Step 3 — This identical block is written simultaneously to:
	•	BPC’s server in Mumbai
	•	NIC’s server in Delhi
	•	Maharashtra State Government’s designated node
Step 4 — Now someone tries to change “Priya” to a fraudulent name on BPC’s server.
What happens: The document hash immediately changes to a completely different string. BPC’s new hash no longer matches the hash on the government’s node. The NIC node also doesn’t match. All three nodes compare every 60 seconds. The mismatch is detected within one minute. An alert is raised. The attempted fraud is logged with timestamp and origin IP. The change is rejected and rolled back.

THE FOUR LOGICAL STEPS EXPLAINED
Step 1 — Why Hash?
A hash is a mathematical fingerprint of a document. Change even one full-stop in the sale deed and the fingerprint changes completely. It is mathematically impossible to produce the same fingerprint from two different documents. This is called SHA-256 — the same algorithm used to secure UPI transactions right now, today, every time you make a payment.
Think of it like this: if you weighed every letter in a document on a molecular scale, the total weight would be unique to that exact document. Change one letter, the weight changes. That is conceptually what hashing does — except it is mathematically provable, not approximate.
Step 2 — Why Distributed?
BPC uses a permissioned private blockchain — meaning only approved, known, trusted nodes can participate. No public access. No anonymous participants. These nodes are: BPC’s server, the NIC or State Government’s server, and an independent audit node.
All three must agree that a record is correct. If BPC’s server is compromised, the government’s copy immediately exposes the fraud. No single entity — not BPC, not a government official, not an outsider — can manipulate a record without all other nodes detecting it.
Step 3 — Why Chained?
Think of old-style official documents where each page is stamped with a seal that references the previous page. If you remove or alter one page, the seal chain breaks and anyone can see it. Each blockchain entry contains the hash of the entry before it. This means you cannot insert, delete, or modify any past entry without breaking the entire chain. The break is immediately visible to all nodes.
Step 4 — What Is the Legal Standing?
The blockchain audit log in BPC is treated as a tamper-evident electronic record under Section 2(1)(t) of the IT Act, 2000. Electronic records are admissible as evidence in Indian courts under Section 65B of the Indian Evidence Act with a proper certificate. We do not need blockchain to be “legalized as title.” We use it as a certified audit trail, which Indian law already recognizes and courts already accept.

ANALOGY FOR THE MINISTER:
Imagine every property transaction is photographed, notarized, and three sealed identical copies are sent to three different trusted government offices in three different cities. If anyone tampers with one copy, the other two immediately expose the fraud. That is exactly what BPC’s blockchain layer does — digitally, automatically, at zero human cost, in under 60 seconds.

SECTION 04 — THE DATA CHALLENGE AND DIGITISATION STRATEGY
The Hardest Problem: Old Paper Records
This is the most practical concern and we will not pretend it is easy.
Decades of property records exist only on paper, in different languages, in different formats, across thousands of registrar offices. Here is a realistic, phased strategy to handle this — using existing government infrastructure, VLEs, and licensed third-party companies — without creating chaos.

HONEST ACKNOWLEDGEMENT:
Digitising India’s complete urban property records is a 5 to 10 year effort across 4,000 plus urban local bodies. BPC’s Phase 1 does not attempt to digitise everything. We start with active transactions and new registrations — where data quality is clean and current — and work backward into legacy records in later phases. Any proposal that claims otherwise is not realistic and should not be trusted.

PHASE 1 — New Registrations (Immediate, from Day 1)
All new property registrations from the first day of the pilot automatically receive a BPC-ID through the Sub-Registrar API connection. Zero manual digitisation effort required — this is live government data being read in real time.
Sources:
	•	Sub-Registrar e-registration API feed
	•	RERA new project registration data
	•	Municipal property tax new entries
What happens: New property registered at Sub-Registrar office today. BPC API reads the registration data within hours. BPC-ID is generated and assigned. Property is now in the system with a verified, government-sourced record. From this point forward, every transaction related to this property is tracked on BPC.

PHASE 2 — Recent Records: Last 10 Years (Year 1 to 2)
Most states already have e-registration systems covering the last 10 to 15 years. Maharashtra has iSarita. Karnataka has Kaveri. Andhra Pradesh has Meebhoomi. These systems hold clean digital records.
BPC pulls this data via API, cross-checks for conflicts across Registrar and RERA records, and assigns BPC-IDs to all matched properties.
Sources:
	•	e-Registration database historical query
	•	RERA registered project and unit data
	•	NHB data on bank-mortgaged properties

PHASE 3 — Legacy Paper Records (Year 2 to 4)
This is the most complex phase. Pre-digital records — some going back decades — exist only as paper in physical files. Three approaches are used in combination:
Approach 1 — DILRMP Scanned Data: The Digital India Land Records Modernisation Programme has already scanned significant volumes of land records. BPC integrates with DILRMP’s data repository to pull already-scanned records.
Approach 2 — VLE Ground Network: Village Level Entrepreneurs under the CSC (Common Service Centre) scheme are government-certified operators. They physically visit registrar offices, scan documents with GPS-tagged mobile devices, and upload to BPC. They are collectors only — they have no authority to verify or approve anything.
Approach 3 — Licensed Data Companies: Companies that have aggregated property data are used as a secondary cross-reference only — never as primary source. Their data is always secondary to Registrar records.

PHASE 4 — Disputed and Unclear Records (Ongoing, Permanent)
Some records will have conflicting data across multiple government systems. The Registrar says Owner A. The Revenue Department’s RoR says Owner B. The municipal records say Owner C.
BPC does not auto-resolve these. The Conflict Detection Engine flags them and routes them to the appropriate government officer’s dashboard for human review. The officer resolves using the source hierarchy. The decision is logged permanently.

HOW VLEs ARE KEPT HONEST
VLE fraud — fake uploads, wrong data entry, collusion with local agents — is a real risk. Here is how it is controlled:
Every upload is automatically tagged with GPS coordinates, exact timestamp, and device ID. This cannot be manually entered — it is captured by the device automatically.
Two independent VLE uploads of the same document must match before data is accepted. If two VLEs upload different data for the same property, both are flagged and the record goes to human review.
AI cross-checks the scanned document image against the Registrar’s text record. If the scanned document’s content does not match the official record, it is rejected automatically.
Every VLE has a running accuracy score. High complaint rate or low accuracy score triggers suspension and investigation.

HOW THIRD-PARTY DATA COMPANIES ARE USED — AND KEPT CONTROLLED
Companies like Spydra, Landed, or NoBroker Data have aggregated property data from various sources. BPC may license this data for cross-referencing only — never as a primary source.
The dependency strategy is clear and time-bound:
Phase 1: Use third-party APIs as supplementary cross-reference
Phase 2: Mirror relevant data internally, reduce API dependency
Phase 3: BPC’s own dataset from government sources becomes primary, third-party becomes optional redundancy
We never allow the core system to permanently depend on a private commercial company for legally critical data. The exit strategy is built in from day one.

THE SOURCE HIERARCHY — WHO WINS WHEN RECORDS CONFLICT
This is the most important rule in the entire system. When two or more sources have conflicting information about a property, the following hierarchy determines which source is authoritative. This hierarchy is hard-coded in system rules and cannot be overridden by any software or any individual user:
	1.	Court Order — overrides everything without exception
	2.	Sub-Registrar Record — final legal title authority under Registration Act 1908
	3.	Revenue Department / Talathi RoR Record — for possession and mutation
	4.	RERA Registration — for new developments under RERA Act 2016
	5.	Municipal Records — property tax records, building permissions
	6.	Third-Party Data — reference only, never authoritative, never used to resolve disputes
	7.	User Uploaded Documents — lowest trust level, always requires official verification

SECTION 05 — BPC vs DigiLocker: THE COMPARISON
Why BPC Is Structurally Identical to DigiLocker — and Stronger
The Ministry trusts DigiLocker. It has been operational since 2015, handles over 6 billion documents, and is trusted by courts, banks, and government departments. Here is an exact comparison showing that BPC is built on the same foundations.

WHAT DIGILOCKER DOES:
	•	Documents stored in government-controlled cloud infrastructure
	•	Aadhaar-linked login for citizen identity verification
	•	IT Act 2000 digital signatures on issued documents
	•	Legally valid — accepted by courts, banks, and all government departments
	•	Documents cannot be altered once issued by the source authority
	•	Issuer — the government department — retains source authority
	•	Encrypted storage and SSL transmission
WHAT DIGILOCKER DOES NOT DO:
	•	No cross-department conflict detection (Registrar vs RoR vs Municipal)
	•	No transaction trail linking buyer, seller, and registration in sequence
	•	No fraud flag or risk scoring for banks or buyers
	•	No audit chain — if a source department corrupts its own data, DigiLocker has no check

WHAT BPC DOES — SAME FOUNDATIONS AS DIGILOCKER:
	•	Documents stored across distributed nodes: BPC plus Government plus NIC — stronger than single-location DigiLocker storage
	•	Aadhaar OTP and biometric login — identical to DigiLocker
	•	IT Act 2000 digital signatures — identical legal standing to DigiLocker
	•	Legally valid under IT Act and Indian Evidence Act Section 65B
	•	Records cannot be altered — SHA-256 hash plus blockchain audit log enforces this
	•	Registrar retains source authority — BPC is a read and verify layer only
	•	AES-256 encryption plus TLS 1.3 — equal to or stronger than DigiLocker standard
WHAT BPC ADDS THAT DIGILOCKER CANNOT DO:
	•	Cross-department conflict detection: flags when Registrar, RoR, and Municipal records disagree
	•	Full transaction trail: token money receipt, Agreement to Sale, and Registration are all linked under one BPC-ID
	•	AI fraud flags and risk scoring: gives banks and buyers an objective risk assessment before they commit
	•	Blockchain audit chain: even if a source government department’s data is tampered with internally, the audit chain exposes the discrepancy

SUMMARY FOR MINISTRY:
BPC is DigiLocker, purpose-built for property transactions, with four additional capabilities that DigiLocker was never designed to provide. We are not reinventing a trusted system. We are extending the same trusted architecture into the domain of property — where the need is most urgent and the consequences of fraud are most severe.

SECTION 06 — ANTICIPATED MINISTRY QUESTIONS
Every Hard Question With a Direct, Complete Answer

QUESTION 1: “Blockchain is not legalized in India. How can you use it?”
Correct — there is no specific Blockchain Act in India. However, we are not asking for blockchain to be recognized as a legal title instrument. BPC uses blockchain as a tamper-evident electronic record system, which is fully covered under Section 2(1)(t) of the IT Act, 2000, which defines electronic records. Electronic records produced by computers are admissible as evidence under Section 65B of the Indian Evidence Act, 1872, provided a proper certificate is issued. The Supreme Court of India has upheld this in multiple judgments. We are not asking for new law. We are using existing technology within existing law — exactly as NPCI, UIDAI, and Indian banks do every day.

QUESTION 2: “What if BPC’s servers are hacked? All property records could be stolen or changed.”
Three answers.
First: BPC’s servers hold a copy of property records. The original, legal, authoritative record always remains with the Sub-Registrar. A hack of BPC’s servers does not affect the legal title under Registration Act 1908.
Second: Our data is AES-256 encrypted at rest and TLS 1.3 encrypted in transmission. Even if the server is physically stolen, the data is completely unreadable without decryption keys, which are stored separately in a Hardware Security Module that cannot be remotely accessed.
Third: The blockchain audit log is distributed across three independent nodes including a government-controlled node. Changing data on BPC’s server without also changing the identical entry on the government’s node is technically impossible. The mismatch is detected automatically within 60 seconds.
The most important context: this system is more secure than the current paper-based system, which can be physically lost, destroyed in a fire, or forged with zero automated detection.

QUESTION 3: “Who owns the data? Can BPC sell citizen property data to private companies?”
Citizens own their data. BPC is a data processor, not a data owner, under the Digital Personal Data Protection Act 2023. No property data can be shared with any third party without the explicit digital consent of the property owner. The system has a Consent Engine built in — citizens control who sees their data: a bank, a potential buyer, or a government officer.
BPC signs a Data Processing Agreement with the Ministry that legally prohibits commercial sale or misuse of citizen data. Violation is a criminal offence under the DPDP Act. We welcome a government-appointed independent data auditor to review our systems at any time without notice.

QUESTION 4: “Sub-Registrar offices still work on paper. How will this practically work?”
BPC does not require Sub-Registrar offices to change their workflow in Phase 1. The integration is read-only and API-based. Most states already have e-registration systems — Maharashtra has iSarita, Karnataka has Kaveri, Andhra Pradesh has Meebhoomi, Telangana has CARD. BPC connects to these existing portals via approved APIs to fetch registration data.
For offices without APIs, BPC works with the respective state’s NIC team to build a lightweight data bridge. We are not asking every Sub-Registrar to learn new software. We work with what exists. We add a verification and audit layer on top. The Sub-Registrar’s role and authority is unchanged.

QUESTION 5: “Two different states have different land record systems. How does BPC handle this?”
This is the real engineering challenge and we have a clear answer. BPC uses a State Adapter Layer — a set of custom connectors, one per state system. Maharashtra’s iSarita produces different data formats than Karnataka’s Kaveri or AP’s Meebhoomi. Our adapters normalize all of these into a single unified BPC data schema.
This is the same architectural pattern used by NeSL — National E-Governance Services Limited — for IBC insolvency data across multiple states. It is a proven approach. We pilot in two states in Phase 1, build adapters for two more states in Phase 2, and scale state by state with NIC collaboration.

QUESTION 6: “What happens if BPC as a company shuts down or gets acquired?”
This is a legitimate governance concern and we have a hard commitment in response.
The government always holds an independent and complete copy of all BPC audit chain data, because the blockchain audit log is distributed and the government’s node holds a full copy at all times. A BPC shutdown does not result in data loss for the government.
We propose a Data Escrow clause in the Ministry MoU requiring BPC to deposit complete system backups with NIC every 30 days. All the underlying property records are government data to begin with — they originate from government sources and return to government custody. BPC’s unique contribution is the audit chain logic and conflict detection layer, and we commit to transferring this codebase to the government in the event of BPC’s dissolution.

QUESTION 7: “What stops a corrupt government officer inside the system from manipulating records?”
This is the most important governance question and the answer is the design of the system itself.
Every action taken by every officer inside BPC — every approval, every flag, every override — creates an immutable blockchain log entry with the officer’s digital identity, timestamp, and exact action performed. This entry cannot be deleted. It cannot be edited. It exists across three nodes simultaneously.
For critical operations — overriding a conflict flag, approving a mutation, resolving a disputed record — a 4-Eyes rule applies: two separate officers from different departments must independently authorize the action with their digital signatures. Neither officer can see the other’s decision until both have decided independently, preventing collusion.
The Ministry’s own designated audit officer has read-only access to the complete activity log of all government officers using the system, in real time, without prior notice to those officers.

SECTION 07 — THE THREE SENTENCES EVERY MINISTER MUST REMEMBER
Sentence 1 — On Security:
Every property record has a mathematical fingerprint stored simultaneously in three independent locations including a government-controlled server, and any change to any record in any location changes that fingerprint and triggers an immediate alert across all three locations within 60 seconds.
Sentence 2 — On Legality:
BPC uses no technology that requires new legislation — the IT Act 2000, Indian Evidence Act Section 65B, DPDP Act 2023, and RERA Act 2016 together provide complete legal coverage for every function BPC performs, with the legal title record always remaining with the Sub-Registrar as required by the Registration Act 1908.
Sentence 3 — On Government Authority:
BPC never automatically approves any property transaction — technology detects and flags, a government-authorized officer decides, and every decision is permanently logged in a system that even BPC’s own engineers cannot edit without it being detected.

THE CLOSING ARGUMENT
India’s current paper-based property system can be defrauded with a forged stamp, a cooperative clerk, and ₹50,000.
BPC requires an attacker to simultaneously:
	•	Compromise three independent servers in different physical locations
	•	Break AES-256 encryption keys held in a Hardware Security Module
	•	Compromise the government’s own blockchain audit node
	•	Forge a government officer’s IT Act digital signature
	•	Do all of the above without triggering any of the automated anomaly detection alerts that run every 60 seconds
That is not a realistic attack vector.
The question is not “Is BPC perfectly secure?” — no system in the world is perfectly secure.
The question is: “Is BPC more secure than paper?”
The answer is categorically, demonstrably, and technically yes.
